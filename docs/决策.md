# 决策记录

## ADR-001：桌面壳用 pywebview，而不是 Tkinter / Qt / Electron

- 背景：用户要 Windows 桌面小工具，要求交互顺、运行快；参考产品的优点主要来自网页画布的缩放/拖拽/就地编辑。
- 决策：Python + pywebview（WebView2）做原生窗口，前端用无框架 HTML/CSS/ES modules；打包为 onefile exe。
- 原因：网页层最容易做到顺滑和清晰排版；pywebview 比 Electron 轻，比 Tkinter 的交互上限高；不需要引入 React/Vite 构建链。
- 代价：需要 WebView2 Runtime；windowed exe 的 stdout 不可靠，smoke 结果需落文件；前端是 JavaScript，不是纯 Python。
- 备选：Tkinter（轻但交互天花板低）、PySide6（原生但重写成本高、分发更大）、Electron（体积大）。

## ADR-002：对同类项目做 clean-room，不复制代码

- 背景：`trace-by-hand-whiteboard` 的功能清单与用户需求高度重合，但仓库当前没有 LICENSE（默认保留所有权利）。
- 决策：只参考功能方向与交互思路；代码、页面、资源全部独立实现；README 明确致谢并说明未复制。
- 原因：没有许可证不能直接下载、修改、再分发；MIT 发布要求代码来源干净。
- 代价：组件实现成本更高；一些交互细节需要自己打磨。
- 后续：如果作者补充了宽松许可证，可再评估借鉴具体实现。

## ADR-003：步骤快照 + 自动差异是核心，不执行代码

- 背景：用户的目标是“想通后写出来”，不是调试器；自动追踪会引入执行安全和产品偏移。
- 决策：当前状态可编辑；记录一步时保存全量快照；时间线回看；差异自动高亮。全程手动，不执行用户代码。
- 原因：快照模型简单、可验证、易于撤销和序列化；差异直接回答“这一步变了什么”；手动保证工具不替用户思考。
- 代价：步骤多时文件会变大（目前规模很小，可接受）；不能自动从代码生成步骤。

## ADR-004：布局/标注与状态分离

- 背景：如果每步都保存对象位置，翻步骤时卡片会跳动；如果标注也是状态，用户每步都要重画箭头。
- 决策：对象位置、卡片尺寸、便签、连线、画笔是持久对象；只有数据卡片的值、标记和指针位置进入步骤快照。
- 原因：比较状态时布局稳定；标注只需画一次；差异聚焦在“数据变了什么”。
- 代价：在历史步骤中不能移动对象（当前明确禁用），要在当前布局中调整。

## ADR-005：本地优先、无遥测、MIT

- 背景：这是个人刷题工具，项目文件可能包含思路和题目数据；用户要公开发布。
- 决策：项目是普通 JSON；桌面 API 只写本机；不联网、不收集数据；MIT 许可证；发布 Pages 项目主页和 Release。
- 原因：隐私和可移植性；MIT 与 PySide6 等 LGPL 依赖兼容（本项目不用 PyQt6 的 GPL 绑定）。
- 代价：没有云同步和协作；跨平台需要另外打包验证。

## ADR-006：画板数据统一放应用旁边的 boards/

- 背景：旧版把当前会话放在 `%APPDATA%/ThinkingCanvas`，画板概念不清晰，用户也要求不要散落在 C 盘或项目各处。
- 决策：所有画板以 `board-<id>.tcanvas.json` 放在应用旁边的 `boards/`；当前画板自动保存；删除移到 `boards/.trash/`；启动时打开最近修改的画板，没有则新建一个。
- 原因：位置单一、可备份、可迁移；源码运行和 exe 运行规则一致；不依赖用户目录。
- 代价：exe 需要放在可写目录；文件名使用稳定 ID，标题从内容读取，不能靠文件名识别画板。

## ADR-007：前端常驻文案只保留操作必需

- 背景：说明性文字和提示让界面显得拥挤；用户明确要求把简洁写进前端设计规范，并在其他项目默认执行。
- 决策：常驻界面只保留操作必需文字；解释、快捷键、教学放帮助弹窗或 `title`；toast 只用于失败和不可见结果；状态提示改为自动消失的浮层，不再占固定布局行。
- 原因：降低视觉噪声，让数据和操作成为主体；用户不需要在每个项目重复提同一件事。
- 代价：新用户需要打开帮助层才能看到完整说明；新增功能时要主动做减法；对象数量只在状态浮层短暂可见。

## ADR-008：画板与工具拆成两个可拖动栏

- 背景：画板多了以后，单一侧栏里的列表会把下面的工具区不断往下挤；用户要求文件管理与工具管理分栏，并明确要求边界可拖动、考虑极端压缩/展开。
- 决策：工作区改为 7 列 Grid：画板栏 + 分隔条 + 工具栏 + 分隔条 + 画布 + 分隔条 + 检查器。画板栏与工具栏各自内部滚动；三根分隔条可拖、键盘可调、双击复位；宽度存 `boards/.ui-state.json`。
- 极端处理：画板栏压到 44px 变图标轨道（图标+数量，点击恢复），工具栏压到 46px 变图标轨道；展开上限分别为 360px / 220px；检查器 220–420px。窄窗先压检查器，再压画板/工具，画布至少 360px。
- 原因：列表增长不影响工具位置；宽度偏好可跨会话保留；极端状态仍然可操作，不会把内容挤到重叠。
- 代价：`boards/` 里多一个隐藏的 `.ui-state.json` 和一个 UI 状态 API；分栏逻辑比固定侧栏复杂，需要测试边界值。
- 补充：示例画板改为纵向列，配合 56–90px 自适应 fit 留白，避免双栏挤压后示例缩小到不可读。

## ADR-009：状态条浮层化与滚动条隐式化

- 背景：用户指出状态条没必要一直占着底部，滚动条也应在不操作时隐藏，让页面更简洁。
- 决策：状态提示改为画布内的浮层，启动 6.5 秒/操作后约 3 秒自动隐藏，并提供关闭按钮；滚动条 8px、圆角、统一颜色，默认透明，鼠标进入对应栏或容器才显示。
- 原因：不牺牲可发现性：提示在需要时出现；滚动条仍在原位置，只是降低常驻视觉噪声。
- 代价：对象数量不是常驻信息；用户需要移动鼠标到对应栏才能看到滚动条，符合“简洁优先”的取舍。

## ADR-010：示例是固定文件，动作只留一个显眼入口

- 背景：点“示例”每次都会新建一个画板，误触后留下重复；示例被当成“新建”动作放在页脚/空状态/检查器/右键多个位置。同一个“记录一步”在顶栏和底栏各有一个可见按钮；84px 的底栏视觉重心偏重。
- 决策：示例固定为 `boards/board-sample.tcanvas.json`，`ensure_sample_board` 只在缺失时创建，之后始终打开/保存同一文件，并拒绝删除；示例入口改为画板栏底部的固定示例行，删除其余示例入口。记录只保留顶栏蓝色按钮，时间线高度 84→62→48px。
- 原因：示例是“看的对象”而不是“新建动作”；同一动作只留一个显眼入口；压低底栏让画布和时间线更平衡。
- 代价：示例不能被删除；旧版本已经生成的随机示例画板仍作为普通画板保留，需要用户自行清理，不做自动删除。
- 后续：如果旧重复示例成为实际问题，再单独设计“清理旧示例”的确认流程。

## ADR-011：批量输入用代码字面量，卡片按钮必须有动作

- 背景：数组批量输入用 TSV 展示，用户看到的是被拉宽的空格；`+i` / `⋯` / `＋` 没有被绑定点击处理，点了没有反应；`1 × 4` 被误认为张量或“SEN”标签。
- 决策：批量输入接受 `[1, 2, 3]`、`[[1, 2], [3, 4]]`、多行方括号和引号字符串，同时保留 Excel TSV；弹窗用代码格式显示并实时预览行列/条目数。Canvas 统一处理卡片工具：数组 `+i` 加指针、`⋯` 打开批量输入，列表/字典/集合 `＋` 追加一项/行；只读时明确提示。数组尺寸改为 `N 行 × M 列`。
- 原因：代码字面量是用户实际复制的内容，逗号比 Tab 更稳定；按钮要么有动作要么不该出现；中文尺寸标签消除“张量/SEN”误读。
- 代价：解析器要兼容多种粘贴格式；新增卡片工具必须同步接入 `onCardToolClick`，后续测试需要覆盖按钮点击。

## ADR-012：画笔与连线都必须有对象级清理路径

- 背景：用户画出蓝色箭头后无法删除或擦除，只能回档；截图中的箭头实际是连线，旧橡皮擦只识别笔迹，笔迹本身也只有几像素宽，点击很难命中。
- 决策：笔迹额外渲染 16px 透明命中带；连线的命中带从 12px 扩到 16px。橡皮擦（`E`）点击或拖过时同时识别笔迹和连线；选中对象仍走统一的 `deleteSelection`，连线右键补“删除连线”。橡皮擦不擦数据卡片和矩形，避免误删整张卡；它们通过选中/`Delete`/右键清理。
- 原因：画得出来的内容必须有非回档的清理路径；命中富余度解决“线太细点不中”；橡皮擦只处理墨迹类对象，保留卡片的结构化操作和撤销语义。
- 代价：命中带比可见线宽，密集重叠时需要先放大再擦；一次拖动只压一个历史快照，不能按单笔细分撤销。

## ADR-013：单实例入口按心跳判断健康，而不是只按窗口存在

- 背景：用户反馈 Web 预览稳定、APP 打开始终有问题。实测正常启动 5/5 约 0.7 秒出窗口；故障来自旧窗口的 WebView2 崩溃后变黑，但进程和命名 mutex 仍在，后续启动只按标题找到黑窗口并聚焦，永远不会起新窗口。Web 与 APP 不共用后端进程。
- 决策：正常运行实例写 `%TEMP%/ThinkingCanvas/instance.json`（PID、exe、窗口句柄、状态、心跳）；前端 `app.start()` 后 `boot_ready`，之后每 2 秒心跳。二次启动遇到 mutex 占用时恢复并聚焦旧窗口，观察心跳 6 秒（启动中 12 秒）：心跳前进则只聚焦；不动则校验 PID/exe、终止旧实例及 WebView2 子进程，重试 mutex 后用恢复 profile 起新实例。无标记旧窗口先给 3 秒宽限，仍无标记则校验进程镜像后替换；25 秒无握手由启动看门狗弹原生错误并退出。
- 原因：窗口存在不等于界面活着；心跳能区分黑窗口、启动中和最小化的健康窗口；入口必须能自恢复，不能要求用户去任务管理器手工清进程。
- 代价：每 2 秒一次小文件心跳；替换陈旧实例需要约 6–12 秒；终止进程必须校验 PID 对应的镜像路径，避免 PID 复用误杀。

## ADR-014：品牌图标以 `app.ico` 为唯一图形源

- 背景：exe 文件有品牌图标，但运行时窗口/任务栏回退成 Python 图标；页头又用 CSS 画了一个近似图形，和 exe 图标不一致。
- 决策：以 `app/app.ico` 为唯一图形源。pywebview `start(icon=...)` 设置窗口图标，构建脚本把 `app.ico` 作为数据文件打进包，并设置显式 AppUserModelID；页头和官网使用从同一图形裁出的 `web/brand.png`/`site/brand.png`，不再用 CSS 仿画。
- 原因：Python 默认图标会让工具看起来像脚本；多个近似 Logo 会持续漂移。统一源文件最省心，也便于以后换品牌图时一次替换。
- 代价：包体增加约 23 KB；以后换图标必须同步更新 `app.ico` 与两份 `brand.png`，并重截 hero/empty。
